# web

The Loophole player app: a SvelteKit single-page app (Svelte 5 runes, static adapter with an `index.html` fallback, no server-side rendering). Small boards render as SVG and large ones on a canvas, under one input surface that takes touch, mouse and keyboard input. Boards too big to fit at a tappable size zoom and pan instead of shrinking.

- Game logic (edge history, stopwatch, hit-testing, drag strokes, keyboard cursor, saved progress, theme choice) lives in plain TypeScript modules with `bun:test` tests beside them. Keep those modules free of runes, `$lib`/`$app` imports and DOM access so the root `bun test` runs them. Components stay thin; the Playwright end-to-end tests cover them.
- One set of board geometry and zoom math serves both renderers and all input: a board point is the viewport point plus the view offset, in pixels at the current cell size. A new kind of mark has to be drawn in both the SVG and the canvas renderer.
- Rule checks and completion come from the core package (`analyzeBoard`), not from code here.
- Screens get puzzles through the puzzle source interface. The built-in fixtures come first, so their ids work with no server running; the rest come from the API through the generated client package. In development Vite proxies `/api` to the API server.
- Hints come through the puzzle source too: built-in puzzles work them out in the browser from their clues (core's `findHint`), server puzzles ask the API. Seeing a hint marks the attempt as assisted in the saved progress.
- Theme colours come from the CSS custom properties in the app stylesheet, which follow the design kit (`docs/design/README.md`). Book-cover tints are the one exception: they are the same in both themes.
- App code type-checks without Bun's types; tests and test helpers use a second config that adds them.
- Saved progress goes through the sync module: guests and built-in puzzles use the guest store in browser storage, as before; a logged-in player's server puzzles keep a copy under the account's own keys and sync with the API. Guest progress joins an account only through the "Add to my account" button, not on login by itself.
- Who is logged in comes from the auth store, a plain module over the generated client with tests beside it. The root layout refreshes it once; the shared site header shows it. The account pages are plain forms styled by the `.auth` rules in the app stylesheet.
- End-to-end tests end in `.e2e.ts` and run with `bun run test:e2e`. They need a local Chromium and are not part of `bun run check`. Frame-time checks are tagged `@perf` and run with `bun run test:perf` instead. The account test ends in `.auth-e2e.ts` and runs against the real API with its own config (`bun run test:e2e:auth`); the user-story tests end in `.story-e2e.ts` and run on the same stack (`bun run test:e2e:stories`).
- The puzzle editor's logic (draft, keys, live check, submitting) lives in plain, tested modules under `lib/editor`; its components stay thin, and its board reuses the play board's renderers.
- The accessibility end-to-end test runs axe-core on each main screen in both themes; a new screen gets a line in its list.
- Only the fonts' Latin subsets block the first paint; the full stylesheets, with the Japanese glyphs, load after it (PRD §10, time to first interaction). Japanese text swaps in late, so keep it out of places where a change of width would move the board.
- Daily puzzles, ranked attempts and leaderboards go through `lib/daily`, plain tested modules over the generated client. The play screen takes an optional `ranked` prop and knows nothing else about ranking. The guest end-to-end tests stand in for the daily API with `page.route` (`tests/daily-mocks.ts`); the end-to-end ports come from `tests/ports.ts` (`E2E_PORT`, `E2E_AUTH_PORT`).
- The large fixtures are generated by a script; change the script and regenerate them rather than editing them by hand.
- Biome lints `.svelte` files but does not format them, because its Svelte formatter is still experimental. Follow the style of the existing components.
