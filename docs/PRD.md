## 1. Summary

Loophole is a responsive web app and server for Slitherlink. It generates puzzles that are verified to have exactly one solution, lets people play them in the browser (touch-first), and gives them a daily puzzle, leaderboards, and the ability to submit their own puzzles.

## 2. Problem and opportunity

Existing Slitherlink sites and apps are either ad-heavy, desktop-oriented, limited in grid size, or do not guarantee uniqueness for user-made puzzles. Players who want large grids, fair hints, and a competitive daily puzzle have no good home.

## 3. Goals

- G1. Every published puzzle has exactly one solution, proven by the server.
- G2. Good play experience on phones, tablets, and desktops, with light and dark themes.
- G3. Square grids up to 100 cells per side.
- G4. A daily puzzle with leaderboards bucketed by size and level.
- G5. Anyone can submit a puzzle, and it is published once proven unique.

## 4. Non-goals (v1)

- Non-square tilings (hex, triangle, etc.).
- Native apps, offline/PWA install, real-time multiplayer.
- Monetization.
- Human moderation of submissions.
- Difficulty ratings (deferred until we know which techniques matter; see §14).
- Submission rate limits and size limits beyond the 100-per-side cap (deferred; small user base).

## 5. Users

| Persona | Needs |
|---|---|
| **Guest** | Play immediately; progress kept locally. |
| **Player** (registered) | Synced progress, history, leaderboard entries, can submit puzzles. |
| **Creator** (a Player who submits) | Enter clues, learn whether the puzzle is unique, share it. |
| **Admin** | Remove abusive or broken content; view system health. |

## 6. User stories

- As a guest, I can start a puzzle in one tap and solve it on my phone.
- As a player, I can leave a puzzle and resume it on another device.
- As a player, I can ask for a hint and understand why the move is forced.
- As a player, I can see how my solve time ranks among puzzles of the same size and level.
- As a creator, I can enter clues and be told if the puzzle is unique, has no solution, or has several.
- As a player, I can play today's daily puzzle and keep a streak.

## 7. Functional requirements

Priority: **P0** = required for launch, **P1** = soon after.

### 7.1 Rules and model
- FR-1 (P0). The puzzle is a rectangular grid of W×H cells, 1 ≤ W,H ≤ 100, with optional clues 0–3 per cell. A solution is a set of edges forming a single closed loop satisfying every clue.
- FR-2 (P0). Wire format for a puzzle: width, height, clue string (row-major, `.` for empty), plus optional seed and metadata. Specified and versioned in `docs/FORMAT.md`.

### 7.2 Solver and verifier
- FR-3 (P0). A rule-based solver applies named deductions (clue-0, clue-satisfied/saturated, dot degree 0/2, corner and adjacent/diagonal 3 patterns, inside/outside parity, premature-loop prevention, bounded lookahead) until stuck, recording which rule fired at each step. Rule groups (corner rules, colouring, connectivity), parity and lookahead can be left out, so a difficulty level can use a smaller set: easy uses only the local rules (clues, dots, the 3s and corner patterns, premature loop), medium adds parity and the corner rules, hard uses every rule and lookahead.
- FR-4 (P0). A verifier returns one of: `unique`, `none`, `multiple`, or `unknown` (time/size budget exhausted). Only `unique` puzzles can be published.
- FR-5 (P0). Verification must be correct: a property-based test suite compares it against brute force on all small grids.
- FR-6 (P1). The solver's step record powers hints (see FR-12).

### 7.3 Generator
- FR-7 (P0). Generation inputs: width, height, optional seed, optional level (easy, medium or hard; default hard). Output: clue grid, solution, and the solver result. A level decides which rules judge each clue removal and solve the result, and how many clues stay (at least 55% of cells at easy, 45% at medium; hard keeps only what its rules need, about 40%). The puzzle records its level (`meta.level`, `docs/FORMAT.md`).
- FR-8 (P0). The generator builds a random loop and rejects loops that are too small or thin. Defaults (tunable): the loop must enclose at least ~40% of cells, and its bounding box must span at least ~80% of both dimensions. Thresholds live in config and have tests.
- FR-9 (P0). Clues are derived from the loop and then removed while uniqueness still holds, so the final puzzle has the same solution and is `unique`.
- FR-10 (P0). Generation is deterministic for a given seed and version.
- FR-11 (P0). Large grids are generated by background jobs with progress and a timeout; they are never generated in the request path.

### 7.4 Player client
- FR-12 (P1). Hint: highlights the cells involved in the next forced deduction, using only the rules of the puzzle's level, and explains the rule in words. Using a hint marks the solve as assisted and excludes it from ranked leaderboards.
- FR-13 (P0). Input: tap/click an edge to cycle line → X → empty; drag to draw. Hit targets are at least 44px on touch devices; pinch-zoom and pan for large grids.
- FR-14 (P0). Undo/redo, timer, pause, and clear.
- FR-15 (P0). Error highlighting only for definite violations: a dot with 3+ lines, a cell with more lines than its clue, a closed loop that is not a full solution, or a clue that can no longer be satisfied. Merely-wrong guesses are not flagged.
- FR-16 (P0). Light and dark themes (follow system, user override).
- FR-17 (P0). Completion is detected client-side and confirmed server-side for ranked puzzles.

### 7.5 Accounts
- FR-18 (P0). Email + password sign-up and login. Passwords hashed with argon2id.
- FR-19 (P0). Sign-up is protected by a CAPTCHA.
- FR-20 (P0). Email verification and password reset.
- FR-21 (P0). Auto-saved in-progress state per puzzle, synced across devices; guests use local storage and can migrate to an account.

### 7.6 Daily puzzle and leaderboards
- FR-22 (P0). One daily puzzle per size class, the same for everyone, switching at 00:00 UTC.
- FR-23 (P0). Leaderboards are bucketed by area (W×H, so 10×15 and 5×30 share a bucket) and level. Rank is by solve time. Hint-assisted solves are excluded.
- FR-24 (P1). Streaks and personal bests.
- FR-25 (P0). For ranked puzzles the server does not send the solution; it validates a submitted solution and sanity-checks timing.

### 7.7 User-submitted puzzles
- FR-26 (P0). An editor lets users set grid size and clues, with live feedback from the solver.
- FR-27 (P0). On submit, the server verifies uniqueness (FR-4). `unique` puzzles are published immediately with no moderation. `none`, `multiple`, and `unknown` are rejected with an explanation.
- FR-28 (P1). Users can report puzzles; admins can unpublish.

### 7.8 Levels
- FR-29 (deferred). "Level" in leaderboard buckets is a placeholder. For v1 all puzzles share one level; the field is kept in the schema so difficulty can be added without a migration. See §14.

## 8. Non-functional requirements

- NFR-1 Performance: generation runs as a background job with progress (FR-11), so it may take longer than a request (decided 2026-10-26): p95 under 10 s for ≤ 30×30 and under 30 s at 40×40, and a 100×100 finishes within the worker's generation time limit (default 30 min). Verification of a submitted 100×100 puzzle completes or returns `unknown` within a fixed time budget (default 30 s).
- NFR-2 Responsiveness: usable at 360 px width with no horizontal page scroll; 60 fps drawing on mid-range phones for grids up to 30×30; large grids use canvas rendering and viewport culling.
- NFR-3 Correctness: solver, verifier, and generator are covered by unit and property tests; CI blocks merges on failure.
- NFR-4 Security: argon2id, CSRF protection, secure cookies, rate limits on auth endpoints, parameterized queries, input validation of puzzle uploads.
- NFR-5 Accessibility: keyboard play on desktop, sufficient contrast in both themes, no information conveyed by color alone.
- NFR-6 Privacy: store only email, password hash, and gameplay data. Provide account deletion.

## 9. Technical considerations

- **Language:** TypeScript end to end.
- **Shared package** (`packages/core`): grid model, rules, solver, verifier, format parsing. Used by the server for generation/verification and by the client for hints and validation.
- **Server:** Node or Bun, REST API, Postgres, and a worker pool (worker threads) for generation and verification with hard timeouts.
- **Client:** SvelteKit, SVG for small grids and canvas for large ones.
- **Anti-cheat:** ranked solutions never sent to the client; server validates.
- **Hosting:** not a focus for v1. A reserved instance that already hosts another of the owner's services is a candidate. Decision deferred.
- **Scale risk:** exhaustive uniqueness proofs do not scale to 100×100 in general. The generator therefore targets puzzles that the rule-based solver (with bounded lookahead) can solve without guessing, because that proves uniqueness. User submissions use the same solver within a time budget and are rejected as `unknown` if not provable.
- **Repo layout (proposed):** `packages/core`, `apps/server`, `apps/web`, `docs/`.

## 10. Success metrics

- 100% of published puzzles are verified `unique` (zero known counterexamples).
- Generator acceptance: ≥ 95% of generated loops meet the coverage thresholds without manual intervention.
- p95 time-to-first-interaction on a mid-range phone under 2 s.
- Day-7 retention and daily-puzzle completion rate (targets set after launch data exists).
- Fraction of submissions rejected as `unknown` (to tune the time budget).

## 11. Milestones

1. **M1 Core:** format, grid model, rule solver, verifier, brute-force cross-check tests.
2. **M2 Generator:** loop generation with coverage thresholds, clue removal, determinism, benchmarks.
3. **M3 Playable client:** guest mode, input, undo/redo, error highlighting, themes, mobile layout.
4. **M4 Server and accounts:** API, database, sign-up with CAPTCHA, verification, saved progress.
5. **M5 Hints.**
6. **M6 Daily puzzle and leaderboards.**
7. **M7 Submissions:** editor and verification flow.
8. **M8 Launch:** hardening, monitoring, deployment, account deletion.

## 12. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Uniqueness proof too slow on large grids | Large puzzles can't be published | Rule-based generation, time budgets, `unknown` rejection |
| Spam/abuse without moderation or rate limits | Junk content, load | CAPTCHA now; add rate limits and reporting (FR-28) when needed |
| Generated puzzles are dull (thin or tiny loops) | Poor quality | Coverage thresholds (FR-8), review sample sets |
| Cheating on leaderboards | Rankings lose meaning | Server-side validation, timing checks, hint exclusion |
| Performance on phones with large grids | Bad mobile experience | Canvas, viewport culling, pinch-zoom |

## 13. Name and branding

Working name: **Loophole** (pun on the loop you draw and the "way out" of a logic trap). Logo concept: a dot grid with one continuous line closing into a keyhole shape; dark theme uses a pale line on deep navy, light theme ink on warm white, with one accent color on the closing segment. Domain and trademark are unchecked. Alternatives: Fence Sitter, Knot Quite, Dotty.

## 14. Open questions

1. Difficulty: which techniques define levels? Answered for the generator (WT20, `docs/DECISIONS.md`): three levels, easy, medium and hard, set by the rules the solver may use and how many clues stay (FR-3, FR-7). Serving them (the generate request, the daily level, leaderboard buckets) is still open; until then the server makes and serves one level, hard.
2. Hosting target and database choice (Postgres assumed).
3. CAPTCHA provider (e.g. hCaptcha, Cloudflare Turnstile).
4. SMTP provider for verification and reset emails.
5. Exact thresholds for loop coverage (FR-8) and the verification time budget (NFR-1).
6. Which size classes get a daily puzzle?
7. Will submission limits and reporting be needed before launch?
